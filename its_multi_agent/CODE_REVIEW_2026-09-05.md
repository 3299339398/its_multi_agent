# ITS 项目代码审查

审查日期：2026-09-05。对象：当前工作区，包含已有未提交修改；不是仅审查 Git HEAD 或某次 diff。未修改业务代码。

## 主要发现

P1 表示应在对外部署前优先处理；P2 表示明确的功能、可靠性或维护问题。以下区分离线复现与静态分析，未把推断写成真实线上事故。

### 1. [P1] 普通用户可以指定服务器访问的模型地址

- 位置：`backend/app/schemas/request.py:41`、`backend/app/schemas/model_profile.py:16`、`backend/app/infrastructure/ai/model_factory.py:64`。
- `base_url` 仅限制字符串长度，临时模型和个人模型均可将地址传给服务端 `AsyncOpenAI`。普通登录用户因此可以驱动服务器向内网或回环地址发出模型协议请求，形成 SSRF 入口。
- 离线校验确认 `http://127.0.0.1:8001/v1` 被接受；未向真实内部服务发起攻击。可访问哪些接口仍受请求路径、方法、目标服务和网络策略限制。
- 建议：由管理员登记允许的供应商端点，用户只选择端点并提交凭据；若必须允许自定义端点，校验协议、解析后的地址及重定向，并设置出站网络限制。本地 Ollama 等端点由管理员显式授权。

### 2. [P1] 退出登录没有清空前端保存的模型密钥等用户状态

- 位置：`front/agent_web_ui/src/App.vue:360`、`:396`、`:725`。
- `resetAuthState` 仅清理登录标识和认证存储，`handleLogout` 另外清理输入和会话列表，但没有清空 `customModel.api_key`、`activeTemporaryModel`、附件选择、位置和活动请求。
- 同一页面退出账号 A 再登录账号 B 时，A 的模型配置仍留在组件内；重新打开配置弹窗可能读取/使用 A 的 API Key。尚未结束的流也可能继续更新页面。
- 建议：统一用户状态容器；退出时取消请求、递增请求代次、清除密钥/附件/定位/消息/模型选择。服务端凭据是否加密与浏览器内存清理是两个独立问题。
- 证据：静态追踪退出和恢复流程；未执行真实账号切换。

### 3. [P1] 入库重试没有同步文档状态，删除后的文档会被任务重新写回

- 位置：`backend/knowledge/services/ingestion_task_service.py:76`、`:99`、`:117`；`backend/knowledge/api/routers.py` 的 `delete_document`。
- 重试只把任务表改成 `queued`，文档登记表仍是 `failed`，而删除接口只拦截 `processing`。在重试排队或执行中删除，后台仍可写入索引并调用 `document_registry.complete`，将已删除文档恢复为 `complete`。
- 使用实际类代码、临时 SQLite 和无外部调用的处理器复现：重试后的文档状态为 `failed`；删除后执行任务，状态变回 `complete`。
- 此外，重试采用先查询再无条件更新，`_run` 没有原子领取；并发重试和多个 API 进程的启动恢复均可能重复执行同一任务。
- 建议：任务与文档共享状态事务，使用条件更新领取任务；引入任务版本/租约和删除标记，完成写入必须验证版本。单机可先用 SQLite 实现，不必立刻引入大型消息队列。

### 4. [P1] 默认容器配置没有持久化入库任务数据库

- 位置：`docker-compose.yml:123`、`:133`；`backend/knowledge/config/settings.py:30`。
- 文档登记库、关键词索引和源文件被指向 `/workspace/runtime/knowledge` 并挂载卷，但 `INGESTION_TASK_DB_PATH` 没有被覆盖，默认仍在代码目录下的 `backend/knowledge/data/ingestion_tasks.db`。
- 没有额外环境覆盖时，容器重建会丢失任务记录，已持久化的源文件和文档状态无法由任务恢复流程接管。普通 restart 与删除后重建容器不是同一种情况。
- 建议：显式把任务库放进知识库数据卷，并做“任务处理中重建容器”的恢复检查。
- 证据：Compose 和 Settings 静态对照；未实际重建用户容器。

### 5. [P1] MinIO 密码与 Milvus 连接配置没有衔接

- 位置：`docker-compose.yml:50`、`:65`；`.env.example:74`。
- Compose 为 MinIO 设置自定义账号密码，但 Milvus 仅设置 `MINIO_ADDRESS`，没有对应的访问凭据配置。示例密码也不是默认密码，不能依赖 Milvus 镜像默认凭据访问。
- 建议：通过该 Milvus 版本支持的配置项或配置文件注入一致的 MinIO 凭据，并验证实际写入和查询；仅验证进程健康不够。
- 同一部署还将 `19530` 映射到所有主机接口，未见启用 Milvus 认证的配置。建议默认仅内部网络访问，需要外部访问时再配置认证和网络边界。
- 证据：静态部署风险；本轮未启动 Docker 或验证镜像实际环境。

### 6. [P2] 前端“保存个人模型”与后端请求模型不兼容

- 位置：`front/agent_web_ui/src/App.vue:396`、`:438`；`backend/app/api/routers.py:79`；`backend/app/schemas/model_profile.py:12`。
- 前端提交的对象没有 `id`，后端却使用必填 `id` 的 `ModelProfile` 接收；仓储本身又会生成新的 ID。正常操作在进入路由逻辑前就被 FastAPI 拒绝，返回 422。
- 将前端同形 payload 交给实际 Pydantic 模型，复现 `id: missing`。
- 建议：定义独立的 `CreateModelProfileRequest`，由服务端生成 ID。进一步将同名配置冲突转换为 409，并保留/校验工具、视觉等能力字段，不要在读回时一律硬编码支持。

### 7. [P2] 附件仅参与当前推理，没有进入持久会话

- 位置：`backend/app/services/agent_service.py:59`、`:63`；`backend/app/services/session_service.py:28`、`:53`。
- 用户纯文本先归档，附件之后仅拼入局部 `chat_history`；保存答案时只追加助手消息。下一轮从数据库重建上下文，原图、附件 ID 和提取文本均不存在。
- 使用实际仓储、上下文和会话类，在临时数据库中复现下一轮附件内容消失。附件原始名称也没有作为持久元数据保存，后续只看到 UUID 文件名。
- 建议：消息保存结构化内容与附件引用；附件表保存所有者、原名、类型、状态、提取结果和生命周期。推理时按引用加载，并制定整轮 token/图片预算。

### 8. [P2] SDK 的初始状态事件使应用层自动重试失效

- 位置：`backend/app/services/agent_service.py:139`、`:176`；`backend/app/services/stream_response_service.py:70`。
- 任何 SSE 包都设置 `emitted_output=True`。真实 SDK 在首次模型请求前会发出 `AgentUpdatedStreamEvent`，流处理器将其转为 PROCESS；随后即使模型尚未回答、尚未调用工具的连接故障，也不能应用层重试。
- 用实际 Runner、实际流处理器和离线故障模型复现：`ACTUAL_SDK_MODEL_ATTEMPTS: 1`，首包 `PROCESS`，结束原因 `ERROR`。
- 现有重试测试替换了流处理器并跳过初始事件，因此没有覆盖该问题。这不代表 OpenAI 客户端底层自己的重试也被关闭。
- 建议：分别记录启动状态、答案/推理输出和工具执行状态。是否重试基于真实语义与副作用，不基于“发过任意一个包”。

### 9. [P2] 切换会话时流式响应没有隔离

- 位置：`front/agent_web_ui/src/App.vue:143`、`:683`、`:893`、`:984`。
- 回答过程中仍可点击会话，`selectSession` 替换全局 `chatMessages`，后续旧请求的 SSE 继续写入这同一个数组。于是 A 会话的回答可能显示在 B 会话中，结束清理也作用于全局状态。
- 建议：为每次请求捕获不可变的 session ID 和 request ID，更新对应会话状态；切换时取消旧请求或继续在后台归属原会话。仅隐藏按钮不足以解决延迟回调问题。
- 证据：静态追踪事件回调，未做浏览器 E2E。

### 10. [P2] 流式输出主动压缩空格，破坏代码和 Markdown

- 位置：`front/agent_web_ui/src/App.vue:984`、`:994`；`backend/app/services/agent_service.py:143`。
- 前端将多个空格压成一个，还丢弃某些纯空白 delta。Python 缩进、代码块内文本、Markdown 硬换行会改变，而且结果取决于供应商如何分块。后端保存时另行压缩连续换行，使展示与原始答案也不完全一致。
- 建议：原样拼接和保存模型文本，只在展示层控制布局；用跨 chunk 的缩进、代码围栏、空行和 Unicode 用例验证。
- 证据：静态分析明确的字符串变换。

### 11. [P2] 模型工厂与旧模型初始化并存，单供应商配置不能可靠工作

- 位置：`backend/app/config/settings.py:135`；`backend/app/infrastructure/ai/openai_client.py:17`、`:22`；`backend/app/multi_agent/orchestrator_agent.py:18`。
- Settings 只要求两家供应商至少配置一家，但旧模块导入时无条件创建两家的客户端。没有另一家 Key、也没有 SDK 后备环境 Key 时，导入可直接失败。
- 不传模型 ID 的请求还会使用全局 `orchestrator_agent` 和 `sub_model`，而不是前面已经解析出的模型。只通过 `MODEL_PROFILES_JSON` 配置其他供应商也无法通过现有 Settings 校验。
- 建议：统一模型入口，按角色解析默认 profile，按需初始化客户端；移除业务层对旧全局模型的依赖，启动时校验实际启用的配置。
- 证据：静态调用链分析，未改动用户环境验证冷启动。

### 12. [P2] “摘要”实际上是截断历史，重要事实会消失且成本随历史增长

- 位置：`backend/app/repositories/sqlite_session_repository.py:177`；`backend/app/services/session_service.py:23`；`backend/app/api/routers.py:134`。
- 每条旧消息取前 500 字再只保留最后 4000 字，不是信息压缩。足够多轮以后，早期关键约束被彻底裁掉。临时 SQLite 复现 70 条消息后，第一条约束不在摘要中。
- 每次追加都全量扫描历史重建摘要；准备上下文又多次读取整段历史。会话列表还一次返回所有会话的全部消息。因此“推理只用最近消息”并不意味着数据库和响应也有界。
- 建议：分页返回会话元数据，按需读取消息；以 token 预算维护最近窗口，用增量摘要保留未解决问题、明确约束和重要事实。摘要更新设置消息水位并允许异步失败回退。

### 13. [P2] 同步附件解析与数据库操作位于 async 请求关键路径

- 位置：`backend/app/services/agent_service.py:59`、`:63`；`backend/app/services/attachment_service.py:62`、`:69`。
- PDF、DOCX、XLSX 全量解析和磁盘读取直接在 async 生成器里执行；文本是在提取完后才截为 30000 字。大文件、压缩文件展开或慢磁盘会阻塞同一进程的其他请求。
- 建议：解析交给有限线程池或隔离进程，限制页数/单元格数/解压规模/耗时；先缓存提取结果，再按上下文预算取用。上传还应有用户总配额和过期清理。
- 证据：静态调用链；未做压力测试，无法据此给出 QPS 数字。

### 14. [P2] JWT 密钥轮换会导致已保存的供应商凭据无法解密

- 位置：`backend/app/repositories/model_profile_repository.py:19`、`:42`。
- Fernet 密钥直接由 `AUTH_JWT_SECRET` 派生。更换 JWT 签名密钥后，新进程无法解密历史模型 API Key；仓储没有密钥版本或迁移方案。
- 建议：为存储加密配置独立密钥及版本，采用可读旧版本、写入新版本的轮换流程；不要把签名与存储加密生命周期绑在一起。
- 证据：静态加解密流程分析；未轮换真实密钥。

## 值得保留的设计

- 用户身份由 JWT 决定，而不是信任请求里的用户 ID；鉴权还会核对数据库中的激活状态和角色。
- 密码采用带随机盐的 scrypt，模型列表排除密钥，个人模型密钥采用加密存储。
- 主服务和知识库服务有内部令牌校验，知识库管理操作限制管理员。
- 两个前端的 Markdown 都经过 DOMPurify，已有恶意 HTML 测试。
- 文档身份包含空间、领域和内容摘要；向量写入有确定性 ID 和失败补偿。
- RAG 已有父子块、向量与 BM25、融合排序、可选重排和自适应改写，方向合理。
- 原子工具优先、复杂问题再用子 Agent 的思路合理，应继续通过真实评测控制额外调用成本。

## 更合适的改进思路

1. **收敛调用链。** 普通知识库问题优先检索并返回证据片段，由一个回答模型完成输出。目前知识库自己生成答案，主 Agent 再处理答案，复杂路径还有专家 Agent，增加延迟、费用和引用失真机会。保留知识库独立问答接口，但让 Agent 工具可以选择 retrieval-only。
2. **明确 Agent 的使用条件。** 简单问答一次模型加工具；复杂诊断才升级专家。将任务成功率、首字延迟、总延迟、模型调用次数和成本放进同一张评测表，再决定是否增加智能体。
3. **把消息归档和模型输入分开。** 数据库保存结构化原始消息和附件引用；context builder 负责摘要、token 预算与脱敏。Redis 只是可丢弃缓存，不能成为事实来源。
4. **把入库当作状态机。** 先完成事务状态、唯一领取、删除墓碑、幂等与恢复，再考虑外部队列。数据量小时 SQLite 是合理选择，多实例部署才需要协调能力升级。
5. **先补业务闭环测试。** 优先覆盖“保存模型后查询”“上传附件后追问”“生成中切会话”“退出后换账号”“失败任务重试再删除”“重建容器恢复”。这些比继续增加纯函数单测更能发现当前缺陷。
6. **用数据证明 RAG 参数。** 构造包含无答案、型号混淆、旧版本、跨领域、冲突资料和来源验证的标注集；测 Recall@K、MRR/nDCG、拒答准确率、引用支持度，并做 BM25/向量/重排的消融。不要把手调融合分数当作回答可信概率。
7. **减少部署和维护分支。** 统一模型工厂；聊天页按认证、模型配置、会话、流读取和附件拆分 composable。保留两个前端的前提应是确有独立管理员产品需求，否则共享认证/API/渲染组件即可。
8. **补可复现环境。** 锁定 Python 直接和传递依赖，补后端与 Harness CI、迁移/初始化脚本、实际依赖 readiness。当前服务站 SQL 使用 `repair_shops`，本轮未找到建表或种子 SQL，新环境的数据准备应写成可执行步骤。

建议顺序：先修 P1、安全退出与模型保存；随后处理附件、流式归属、真实重试和任务原子领取；最后做摘要、检索评测、成本优化和模块拆分。暂时不建议扩展新的 Agent 数量。
